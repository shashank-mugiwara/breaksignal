The Data - Generating Distinct Descriptions Every Time

We will use the script below to populate large amounts of data in PostgreSQL. The main objective of this data is to match text, so populating a distinct description for every record is essential to understand how indexes perform with a variety of data. Therefore, there may be some variations with respect to column names in the above schema. We shall use the essential_generators Python package to generate random statements every time.

def run_methods():
    global counter
    for i in range(0, 20):
        try:
            connection = psycopg2.connect(user="dbuser", password="password", host="127.0.0.1",
                                          port="5432", database="postgres")
            cursor = connection.cursor()
            with open('OrderEventsData.csv', 'r') as oe:
                reader = csv.DictReader(oe)
                for line in reader:
                    counter = counter + 1
                    refund_amount = line['refund_amt']
                    if refund_amount is None or refund_amount.strip() == '':
                        refund_amount = float("0.0")
                    else:
                        refund_amount = float(refund_amount.strip().replace(',', ''))

                    payment_amount = line['payment_amt']
                    if payment_amount is None or payment_amount.strip() == '':
                        payment_amount = float("0.0")
                    else:
                        payment_amount = float(payment_amount.strip().replace(',', ''))

                    balance_amount = line['balance_amt']
                    if balance_amount is None or balance_amount.strip() == '':
                        balance_amount = float("0.0")
                    else:
                        balance_amount = float(balance_amount.strip().replace(',', ''))

                    INSERT_QUERY = """INSERT INTO ecommerce.order_events (id, order_id, event_date, reference_no,
                    highlight, sequence_no, is_refund, refund_amount, payment_amount, description, event_type) VALUES (%s, %s, %s, %s, %s, %s,
                    %s, %s, %s, %s, %s); """

                    order_number = str(line['order_id'].replace("'", ''))
                    event_id = str(order_number) + '-' + str(uuid.uuid4())
                    ref_no = line['reference_no']
                    event_date = datetime.datetime.strptime(
                        parser.parse(line['event_date']).date().strftime("%Y-%m-%dT%H:%M:%S.000Z"),
                        '%Y-%m-%dT%H:%M:%S.000Z')
                    description = gen.sentence()
                    event_type = random.choice(event_type_list)

                    is_refund = False
                    if refund_amount > 0:
                        is_refund = True

                    record_to_insert = (event_id, order_number, event_date, ref_no, False, counter, is_refund,
                                        refund_amount, payment_amount, description, event_type)

                    cursor.execute(INSERT_QUERY, record_to_insert)
                    connection.commit()
        except Exception as e:
            print(str(e))
        print('Iteration: {} completed.'.format(i))


if __name__ == '__main__':
    to_do = []
    with ThreadPoolExecutor(max_workers=8) as executor:
        for i in range(0, 8):
            to_do.append(executor.submit(run_methods))
    for future in as_completed(to_do):
        print("future: {}, result {} ".format(future, future.result()))

Use of other data types was also tried, including character varying, text, and char. It made no difference as the underlying datatype is based on PostgreSQL's varlena. The text below is taken from the official PostgreSQL documentation.

There is no performance difference among these three types,
apart from increased storage space when using the blank-padded
type and a few extra CPU cycles to check the length when storing into a
length-constrained column. While character(n) it has performance
advantages in some other database systems, PostgreSQL has no such advantage.
In fact, character(n) it is usually the slowest of the three because of
its additional storage costs. In most situations text or character varying should be used instead.

The Actual Problem of Full-Text Searches

Consider a string delivered and here we need to search for a substring red. The only solution is to iterate all values in subsets and check if any subset contains red. This is because the value can appear anywhere, and a search on an index won't help as we'd still have to compare every value one by one with no way of reducing the set of rows to search through. This leads to slow query performance.

Let us explore a few basic search processes that PostgreSQL offers. To start with, let's go with a full-text search.

To perform a full-text search in PostgreSQL, consider the command below:

SELECT *
FROM ecommerce.order_events
WHERE to_tsvector('english', description) @@ to_tsquery('english', 'shipped');

Copy

to_tsvector parses a textual document into tokens, reduces the tokens to lexemes, and returns a tsvector which lists the lexemes together with their positions in the document. The document is processed according to the specified or default text search configuration. Here is a simple example:

SELECT to_tsvector('english', 'Package shipped via FedEx Express delivery'); #english - configuration specifed to tell Postgres on which config to split

          to_tsvector
------------------------------------------------------
'deliv':5 'express':4 'fedex':3 'packag':1 'ship':2 'via':3

Copy

to_tsquery creates a tsquery value from querytext, which must consist of single tokens separated by the tsquery operators & (AND), | (OR), ! (NOT), and <-> (FOLLOWED BY), possibly grouped using parentheses. In other words, the input to to_tsquery must already follow the general rules for tsquery input. The difference is that while basic tsquery input takes the tokens at face value, to_tsquery normalizes each token into a lexeme using the specified or default configuration, and discards any tokens that are stop words according to the configuration. For example:

SELECT to_tsquery('english', 'shipped & delivery'); #english - configuration specifed to tell Postgres on which config to split

  to_tsquery
---------------
 'ship' & 'deliv'

Copy

Now in order to utilize the full text search functionality, we have to keep a separate vector say description_ts_vector. For every entry that we add into the order_events table we have to update the vector. To do this we might need to write a trigger or script to update individual entry or vector as whole.

Another problem with full text search is that words are broken up according to the rules defined by the language of the text. For example, on PostgreSQL converting Package shipped via FedEx Express delivery to a text vector results in the values deliv, express, fedex, packag, and ship. This means that searching for express or delivery will match the data, but searching for expr will not. To showcase this we can run the following query in PostgreSQL:

To showcase that full token search works

SELECT 1
WHERE to_tsvector('english', 'Package shipped via FedEx Express delivery') @@ to_tsquery('english', 'express');

# Output
---
 1
---

To showcase that partial token search wont work

SELECT 1
WHERE to_tsvector('english', 'Package shipped via FedEx Express delivery') @@ to_tsquery('english', 'expr');

PostgreSQL Trigram Indexes

Trigrams are a special case of the n-gram where n is 3. In the fields of computational linguistics and probability, an n-gram (sometimes also called Q-gram) is a contiguous sequence of n items from a given sample of text or speech. Trigrams are basically words broken up into sequences of 3 letters. Consider the word delivered - the possible trigrams of this word will be:

d e l
e l i
l i v
i v e
v e r
e r e
r e d

Copy

Basically, we need to generate all trigrams and store them into a vector, apply text matching on these, and reverse-find the indexes to fetch desired results. We can skip all this boilerplate code by using PostgreSQL's built-in pg_trgm extension. To demonstrate, we shall use the query below:

select show_trgm('Package shipped via FedEx Express delivery');

                                  trgm's
-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------
{"  d","  e","  f","  p","  s","  v"," de"," ex"," fe"," pa"," sh"," vi",ack,age,ckd,del,ede,ery,ess,exp,fed,hip,ive,kag,"ks ",liv,"ry ",pak,ped,pre,res,sde,"se ",shi,spr,"ss ",ver,via,"x e","xp "}

Copy

A big benefit of this extension is that these trigram indexes can be used by the LIKE and ILIKE conditions without having to change your queries or set up complex full-text search systems. As you can see, the gram size is not more than 3. Additionally, we need to configure the inverted indexes on the desired text.

To create a GIN index (Generalized Inverted Index):

CREATE INDEX CONCURRENTLY order_events_description_trigram_idx
ON ecommerce.order_events
USING gin (description gin_trgm_ops);

Query returned successfully in 7 min 45 secs.

Copy

The use of the pattern_ops strategy reduces the number of different operations that can be performed on indexes. The main reason for having operator classes is that for some data types, there could be more than one meaningful index behavior. Reducing the number of behaviors available for a particular index helps the PostgreSQL query planner to efficiently generate a plan; otherwise, the planner resorts to naive sequential scans.

Best Practices to Follow Based on the Above Observations

  1. Set the minimum number of characters for search to 3, as we are utilizing the PostgreSQL Trigram index approach.
  2. Avoid searching with special characters if the overall length of the word being searched (including the special character) is ≤ 3.
